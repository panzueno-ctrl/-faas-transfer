============================================================
  2. STACK TECHNOLOGIQUE ET HÉBERGEMENT (GOLDEN STACK)
============================================================

🌐 Frontend (Interface) : Vercel
   - Rôle : Héberge l'application web/mobile compilée (React Native Web / Expo).
   - Pourquoi : C'est le meilleur CDN mondial. Le site se charge instantanément n'importe où.
   - Limites (Plan Gratuit) : 100 Go de bande passante par mois. Largement suffisant pour l'interface.
   - NB : Déploiement automatique à chaque `git push` sur la branche main de GitHub.

⚙️ Backend (Serveur) : Render (Remplacement de Railway)
   - Rôle : Héberge le serveur Node.js / Express qui gère l'API (upload, download, conversions).
   - Pourquoi : Plan gratuit qui ne s'arrête pas après quelques jours.
   - Limites (Plan Gratuit) : 512 Mo de RAM. Le serveur s'endort après 15 min d'inactivité (spin down), ce qui cause un délai de ~50s au premier chargement de la journée (cold start).
   - NB : Bien surveiller la consommation de RAM lors des conversions de gros fichiers.

🗄️ Base de données & Stockage : Supabase
   - Rôle : PostgreSQL pour stocker les métadonnées (table `transfers`), et Buckets pour les fichiers.
   - Pourquoi : L'alternative backend-as-a-service gratuite la plus puissante du marché.
   - Limites (Plan Gratuit) : 500 Mo de base de données. Stockage de fichiers de 1 Go.
   - NB : Le stockage limité (1 Go) justifie l'importance de notre suppression automatique (cron/fin de download). Si le quota est atteint, l'application crashera lors des uploads.

💾 Code source : GitHub
   - Rôle : Versionnement (Git) et sauvegarde du code.
   - Pourquoi : Indispensable pour l'intégration continue (CI/CD) avec Vercel et Render.
   - Limites (Plan Gratuit) : Quasi illimité pour notre usage.
   - NB : Les variables d'environnement (clés secrètes) ne doivent JAMAIS y être poussées. C'est à ça que sert le `.env` (ignoré grâce au `.gitignore`).

============================================================
  4. API ENDPOINTS & FLUX COMPLET
============================================================

  TRANSFERT (Flux End-to-End)
  ─────────────────────────────────────────────────────────
  POST /upload
  1. Le client envoie le fichier (après une éventuelle conversion locale).
  2. Le serveur stocke le fichier dans Supabase Storage.
  3. Le serveur crée une entrée dans la table `transfers`.
  4. Le serveur retourne l'id unique à l'app.
  5. L'app affiche le QR code / Lien / Code à 6 chiffres.

  GET /download/:id
  1. Le destinataire visite le lien ou entre le code.
  2. Le serveur récupère le fichier depuis Supabase et l'envoie.
  3. Le fichier est marqué `downloaded = true` et supprimé après 60 secondes.

  DELETE /expire/:id
  - Supprime manuellement le fichier de Supabase et de la base de données.

  CONVERSION (Flux End-to-End)
  ─────────────────────────────────────────────────────────
  POST /convert/[type]
  1. L'app envoie le fichier au serveur.
  2. Le serveur convertit via LibreOffice/ImageMagick/Poppler.
  3. Le serveur retourne le fichier converti.
  4. L'app propose de télécharger ou de transférer le fichier directement.

============================================================
  7. HISTORIQUE DES DÉCISIONS & RÉSOLUTION DE BUGS
============================================================

  A. Déploiement Initial du Serveur Express
  ─────────────────────────────────────────────────────────
  - Objectif : Recevoir fichier HTTP → Supabase Storage → Retourner ID → Download via ID.
  - Étapes : Structure dossiers → Init Node.js → Config .env → Supabase services → Endpoints → Tests.

  B. Problème de compatibilité Node.js en Production
  ─────────────────────────────────────────────────────────
  - Symptôme : Crash du serveur lors du déploiement initial.
  - Cause : La plateforme utilisait Node 18 par défaut. `@supabase/supabase-js` récent requiert Node 20 (APIs WebSocket natives).
  - Solution : Ajout de `"engines": { "node": ">=20.0.0" }` dans `package.json` pour forcer la version.

  C. Problème "Lien expiré ou invalide" après Upload
  ─────────────────────────────────────────────────────────
  - Symptôme : Même après un upload réussi, le téléchargement échouait immédiatement.
  - Cause racine : Le code supprimait la ligne de la base de données PENDANT l'envoi du fichier, et non APRÈS. Les navigateurs faisant souvent deux requêtes HTTP (ex: pré-chargement), la deuxième trouvait la ligne déjà supprimée par la première.
  - Solution : Utilisation de l'événement `res.on('finish')`. La suppression s'effectue désormais de manière différée (après 60 secondes) garantissant que la réponse HTTP est 100% transmise au client avant le nettoyage.

  D. Écran blanc (Crash) lors de la génération du QR code
  ─────────────────────────────────────────────────────────
  - Symptôme : Lors de l'envoi d'un ou plusieurs fichiers, la barre de progression atteint 100% puis l'écran devient complètement vide, sans QR code ni lien.
  - Cause racine : Deux erreurs combinées. L'adresse du backend dans le code mobile comportait une faute de frappe (`https://-faas-transfer...`). Lors du crash silencieux de la requête, le frontend tentait de générer un QR code avec un lien vide, ce qui faisait crasher le composant `react-native-qrcode-svg`.
  - Solution : Correction de l'URL du backend vers `https://faas-transfer.onrender.com` dans `send.tsx` et `receive.tsx`.

  E. Problème de Transfert Multiple (ZIP) et Saturation Mémoire
  ─────────────────────────────────────────────────────────
  - Symptôme : Le transfert de plusieurs fichiers échouait côté serveur, ou générait une archive corrompue difficile à ouvrir sur mobile.
  - Cause racine : 
    1. Le serveur chargeait l'intégralité du ZIP dans la RAM avant l'envoi à Supabase, ce qui plantait les petits serveurs (Render).
    2. Les noms de fichiers avec espaces cassaient la commande de compression.
    3. Le nom final de l'archive n'était pas défini (`undefined`), corrompant parfois l'extension.
  - Solution : Passage sur une lecture en continu (Stream) via `fs.createReadStream()`. Protection des chemins de fichiers avec des guillemets dans la commande `zip` et forçage de l'option `-j` pour éviter l'inclusion de dossiers temporaires. Génération d'un nom de fichier sécurisé "Archive de X fichiers.zip".

  8. RÉFÉRENCEMENT NATUREL (SEO) SUR GOOGLE
============================================================

  Le référencement (SEO) permet à l'application d'apparaître 
  dans les résultats de recherche Google quand on tape "FaaS Transfer".
  Étant donné que c'est une application dynamique (React/Expo), 
  Google a besoin d'aide pour la lire.

  A. FICHIERS STATIQUES (Dossier : mobile/public/)
  ─────────────────────────────────────────────────────────
  - robots.txt : Fichier lu en premier par les robots de Google. 
    Il leur donne la permission d'explorer toutes les pages du site.
  - sitemap.xml : C'est le "plan de la ville". Il liste toutes 
    les pages importantes (Accueil, Envoyer, Recevoir, Convertir) 
    pour que Google n'en rate aucune.

  B. BALISES META (Fichier : mobile/src/app/_layout.tsx)
  ─────────────────────────────────────────────────────────
  - Composant <Head> d'expo-router : Injecte des balises HTML invisibles.
  - <title> : Le grand titre bleu cliquable sur Google.
  - <meta name="description"> : Le petit texte descriptif noir en dessous du titre.
  - <meta property="og:..."> : (Open Graph) Les images et textes qui 
    s'affichent quand on partage le lien sur WhatsApp, Twitter ou LinkedIn.

  C. PROCÉDURE DE MISE EN LIGNE (GOOGLE SEARCH CONSOLE)
  ─────────────────────────────────────────────────────────
  Une fois les balises meta et le sitemap créés, voici les étapes pour 
  forcer Google à référencer l'application (à faire soi-même sur le web) :
  
  1. Se connecter à Google Search Console : https://search.google.com/search-console
  2. Ajouter une propriété via "Préfixe de l'URL" (ex: https://faas-transfer.vercel.app).
  3. Valider la propriété avec la méthode "Balise HTML" :
     - Copier la balise `<meta name="google-site-verification" content="..." />`
     - La coller dans le `<Head>` du fichier `_layout.tsx`.
     - Faire un `git commit` et un `git push`.
     - Attendre le déploiement sur Vercel (environ 2 minutes).
     - Cliquer sur le bouton "VALIDER" sur Google Search Console.
  4. Une fois validé en vert, aller dans le menu "Sitemaps" (à gauche).
  5. Entrer `sitemap.xml` et cliquer sur "Envoyer".
  
  Résultat : Google scanne officiellement le site et l'affiche dans ses 
  recherches dans les jours qui suivent.

  9. LIMITES TECHNIQUES DE L'ARCHITECTURE ET CRASHS MÉMOIRE
============================================================

  A. Diagnostic des Crashs (Vidéos et envois multiples)
  ─────────────────────────────────────────────────────────
  Symptôme : Lors de l'envoi de gros fichiers (vidéos de 100Mo+) ou de plusieurs dizaines de photos, l'application simulait le chargement jusqu'à 90% puis crashait ou retournait à l'accueil silencieusement.
  
  Cause racine sur le Téléphone (Frontend) :
  Le code utilisait `await fetch(file.uri).blob()` pour convertir le fichier avant de l'envoyer. Cette méthode charge l'intégralité du fichier dans la mémoire vive (RAM) du téléphone. Pour une vidéo de 200 Mo, l'application tente d'allouer 200 Mo de RAM instantanément. Le navigateur mobile ou l'OS tue alors le processus pour éviter la saturation.
  
  Cause racine sur le Serveur (Backend) :
  Le serveur lisait également le fichier entier en RAM via `fs.readFileSync()` avant de l'envoyer à Supabase. Le serveur Render (Plan Gratuit) ne possédant que 512 Mo de RAM, il crashait lors de l'envoi de fichiers trop lourds.

  Solutions techniques implémentées (Détail fichier par fichier) :
  
  [MODIFY] mobile/src/app/send.tsx
  - Importation de `Platform` depuis `react-native`.
  - Remplacement du chargement destructif en RAM (`await fetch(file.uri).blob()`) par un envoi direct du fichier depuis le disque local du téléphone en utilisant `formData.append('file', { uri: file.uri, name: file.name, type: file.mimeType })`.
  - Application de cette logique optimisée pour l'envoi d'un fichier unique ET pour les envois multiples. Le téléphone "stream" le fichier au serveur au lieu de le mettre en mémoire vive.

  [MODIFY] server/routes/upload.js
  - Dans la route `/` (envoi simple), remplacement de la lecture totale en mémoire (`fs.readFileSync`) par un stream asynchrone (`fs.createReadStream`) couplé à l'option `duplex: 'half'`.
  - Résultat : Cela crée un tuyau de données direct entre le serveur Render et le stockage Supabase, sans jamais stocker le gros fichier dans la petite RAM (512 Mo) du serveur.

  B. Limites de la "Stack" Actuelle (Version Gratuite)
  ─────────────────────────────────────────────────────────
  Voici les limites techniques imposées par nos hébergeurs gratuits actuels :

  1. Render (Backend Node.js) :
     - RAM : 512 Mo maximum. (Totalement contourné grâce à l'utilisation des Streams évoquée ci-dessus).
     - Veille : Le serveur s'endort après 15 minutes d'inactivité. Le premier transfert peut donc prendre 30 secondes de plus à démarrer le temps que le serveur se réveille.

  2. Supabase (Base de données et Stockage) :
     - Base de données : 500 Mo gratuits (suffisant pour des millions d'entrées).
     - Stockage Total : 1 Go d'espace disque maximum.
     - Limite de taille de fichier par défaut : 50 Mo par fichier. Si vous essayez d'envoyer un fichier de 60 Mo, Supabase le bloquera. 
       *Solution : Vous pouvez modifier cette limite dans les paramètres de votre projet Supabase (Dashboard > Storage > Policies/Settings).*

  3. Vercel (Frontend Web) :
     - Bande passante : Limite de base de 100 Go/mois.
     - Taille des requêtes : Comme nos fichiers transitent entre le téléphone et notre serveur Render (et non pas vers Vercel), Vercel n'impose aucune limite sur le poids de nos transferts !


============================================================
  10. HISTORIQUE DES BUGS RÉSOLUS (ET SOLUTIONS)
============================================================
Ce journal permet de garder une trace de toutes les anomalies rencontrées durant les tests, et de la manière précise dont elles ont été réglées.

  Bug 1 : Le serveur injoignable et l'écran bloqué
  ─────────────────────────────────────────────────────────
  Symptôme : Le chargement montait jusqu'à 100%, puis l'application devenait silencieuse ou affichait une page vide, sans jamais générer de QR code ni de lien.
  Problème : Dans le code de l'application (`mobile/src/app/send.tsx` et `receive.tsx`), l'adresse du serveur backend était mal orthographiée avec un tiret en trop : `https://-faas-transfer.onrender.com`. Cette adresse n'existait pas, la connexion échouait silencieusement.
  Solution : J'ai supprimé le tiret erroné dans les deux fichiers pour restaurer la bonne URL : `https://faas-transfer.onrender.com`.

  Bug 2 : Les QR Codes généraient un lien mort (Railway)
  ─────────────────────────────────────────────────────────
  Symptôme : Après un transfert réussi, le QR Code scanné par un autre téléphone renvoyait vers une page d'erreur Railway.
  Problème : Le backend (`server/routes/upload.js`) générait manuellement le lien de téléchargement (downloadUrl) qu'il renvoyait au téléphone. Ce lien était encore "codé en dur" avec l'ancien nom de domaine de notre premier hébergeur (Railway).
  Solution : J'ai modifié `upload.js` dans la fonction d'upload simple et d'upload multiple, pour remplacer l'ancienne adresse par la nouvelle URL Render correcte.

  Bug 3 : Mauvais logo dans la recherche Google (Logo Vercel)
  ─────────────────────────────────────────────────────────
  Symptôme : En faisant une recherche sur Google ou en envoyant le lien par WhatsApp, c'était le logo par défaut de Vercel (le petit triangle noir) qui apparaissait.
  Problème : Le site web ne possédait pas de "favicon" officiel configuré avec notre logo.
  Solution : J'ai repris le code SVG du logo que j'avais dessiné pour la barre de menu (le "F" bleu/violet avec la flèche). Je l'ai converti en un véritable fichier image (`favicon.svg`, `favicon.png` et `favicon.ico`) que j'ai placé dans le dossier `mobile/public/` et `mobile/assets/images/`. C'est désormais notre identité visuelle officielle.

  Bug 4 : Erreurs de syntaxe JSX (Fichiers en rouge dans l'éditeur)
  ─────────────────────────────────────────────────────────
  Symptôme : Les fichiers `index.tsx`, `send.tsx` et `convert.tsx` s'affichaient en rouge dans votre éditeur (erreurs de code bloquantes).
  Problème : Des balises React (comme `<ActionCard />`) n'étaient pas correctement fermées. De plus, il y a eu une tentative d'utiliser des commentaires classiques `/* */` directement dans le rendu HTML/JSX, ce qui fait planter React Native.
  Solution : J'ai harmonisé la syntaxe des fichiers, refermé toutes les balises correctement et utilisé la syntaxe de commentaire valide pour JSX : `{/* commentaire */}`.

  Bug 5 : L'effet de brillance (Glow) absent sur les blocs principaux
  ─────────────────────────────────────────────────────────
  Symptôme : Vous m'aviez signalé que le grand bloc de l'interface "ne brillait pas" et manquait de dynamisme.
  Problème : Les propriétés d'ombres (boxShadow, shadowColor, elevation) n'étaient pas correctement calibrées pour se superposer au fond sombre, rendant le bloc plat.
  Solution : J'ai ajusté les valeurs de `shadowOpacity`, `shadowRadius` et ajouté des bordures lumineuses subtiles pour donner ce côté professionnel et "néon" à l'application.

  Bug 6 : L'impossibilité de sélectionner/envoyer plusieurs fichiers (100 photos)
  ─────────────────────────────────────────────────────────
  Symptôme : L'application ne permettait pas de sélectionner plusieurs fichiers d'un coup, ce qui gâchait l'utilité pour les gros envois (saisons de séries, albums photos).
  Problème : Le sélecteur de fichier (`DocumentPicker`) n'avait pas l'option multiple activée, et le backend ne savait gérer qu'un seul fichier à la fois.
  Solution : J'ai activé `multiple: true` dans le DocumentPicker, et j'ai créé une toute nouvelle route backend (`/multiple`) capable de recevoir plusieurs fichiers et de les archiver en un seul fichier ZIP robuste avant de l'envoyer sur Supabase.

  11. AMÉLIORATION EXTRÊME DES PERFORMANCES (DIRECT UPLOAD)
============================================================
Le test de 8 secondes (23 Mo) qui prend 40 secondes et reste bloqué à 90% a mis en lumière deux problèmes majeurs dans l'architecture initiale. Pour envoyer des vidéos de 1 heure (plusieurs Gigaoctets) en quelques minutes, l'architecture a été modifiée.

Les deux problèmes initiaux :
1. La fausse barre de progression (Bloquée à 90%) : Dans le code initial de `send.tsx`, l'application utilisait une fausse animation qui montait automatiquement à 90% en quelques secondes (`setInterval`). Elle attendait ensuite que le serveur ait fini son travail pour passer à 100%.
2. Le goulot d'étranglement du serveur (Double Upload) : Le fichier faisait le trajet `Téléphone -> Serveur Render -> Supabase`. Le fichier voyageait deux fois sur le réseau, et le serveur Render agissait comme un goulot.

La Solution Ultime implémentée : "Direct Upload" (L'autoroute)
L'architecture a été modifiée pour créer une autoroute directe entre le téléphone et Supabase. Le serveur Render sert uniquement de "Guichet".
1. Le téléphone demande au serveur Render : "Je veux envoyer un fichier".
2. Le serveur Render génère un ticket d'accès sécurisé (Signed URL) via Supabase et le renvoie en 0.1s.
3. Le téléphone utilise ce ticket pour uploader le fichier directement à Supabase (1 seul voyage).

Modifications techniques appliquées :
- `server/routes/upload.js` : Création d'une route pour générer des Signed URLs Supabase (retrait de `multer` pour les gros fichiers).
- `mobile/src/app/send.tsx` : Utilisation de `FileSystem.createUploadTask` d'Expo au lieu de `fetch()` pour un suivi de progression 100% réel.
- Librairie `react-native-zip-archive` : Ajoutée pour zipper les fichiers multiples directement en local sur le téléphone avant de les envoyer sur "l'autoroute" Direct Upload.

============================================================
  12. ANALYSE DE L'INFRASTRUCTURE ET LIMITES (CLOUD)
============================================================
Les "nuages" utilisés ne sont pas nos serveurs physiques, mais des services partagés. Sur le plan gratuit, voici les limites exactes qui dictent nos choix d'architecture :

1. Le Disque Dur (Storage Supabase)
   - Limite : 1 Go maximum. Si l'on upload plus de 1 Go de fichiers cumulés, Supabase bloquera les envois suivants.

2. Le Trafic / Bande Passante (Egress Supabase)
   - Limite : 2 Go par mois. Le trafic est consommé uniquement lors des TÉLÉCHARGEMENTS par les destinataires. Si on upload 1 fichier de 500 Mo, et que 4 personnes le téléchargent, on consomme 2 Go (4 x 500 Mo) et le forfait est épuisé.

Solution validée pour repousser ces limites :
Migration future vers Cloudflare R2 qui offre 10 Go d'espace gratuit et une bande passante (trafic de téléchargement) 100% illimitée et gratuite.
