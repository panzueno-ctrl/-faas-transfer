============================================================
  2. STACK TECHNOLOGIQUE ET HÉBERGEMENT (GOLDEN STACK)
============================================================

🌐 Frontend (Interface) : Vercel
   - Rôle : Héberge l'application web/mobile compilée (React Native Web / Expo).
   - Pourquoi : C'est le meilleur CDN mondial. Le site se charge instantanément n'importe où.
   - Limites (Plan Gratuit) : 100 Go de bande passante par mois. Largement suffisant pour l'interface.
   - NB : Déploiement automatique à chaque `git push` sur la branche main de GitHub.

⚙️ Backend (Serveur) : Render (Remplacement de Railway)
   - Rôle : Héberge le serveur Node.js / Express qui gère l'API (upload, download, conversions).
   - Pourquoi : Plan gratuit qui ne s'arrête pas après quelques jours.
   - Limites (Plan Gratuit) : 512 Mo de RAM. Le serveur s'endort après 15 min d'inactivité (spin down), ce qui cause un délai de ~50s au premier chargement de la journée (cold start).
   - NB : Bien surveiller la consommation de RAM lors des conversions de gros fichiers.

🗄️ Base de données : Supabase
   - Rôle : PostgreSQL pour stocker les métadonnées (table `transfers` et système d'authentification `auth.users`).
   - Pourquoi : L'alternative backend-as-a-service gratuite la plus puissante du marché.
   - Limites (Plan Gratuit) : 500 Mo de base de données.

☁️ Stockage de Fichiers : Cloudflare R2
   - Rôle : Héberge physiquement tous les gros fichiers uploadés (vidéos, photos, ZIP).
   - Pourquoi : Stockage cloud ultra-rapide avec CDN mondial intégré.
   - Limites (Plan Gratuit) : 10 Go de stockage. Bande passante (Trafic) 100% ILLIMITÉE !

💾 Code source : GitHub
   - Rôle : Versionnement (Git) et sauvegarde du code.
   - Pourquoi : Indispensable pour l'intégration continue (CI/CD) avec Vercel et Render.
   - Limites (Plan Gratuit) : Quasi illimité pour notre usage.
   - NB : Les variables d'environnement (clés secrètes) ne doivent JAMAIS y être poussées. C'est à ça que sert le `.env` (ignoré grâce au `.gitignore`).

============================================================
  4. API ENDPOINTS & FLUX COMPLET
============================================================

  TRANSFERT (Flux End-to-End)
  ─────────────────────────────────────────────────────────
  POST /upload/request-url (Direct Upload via R2)
  1. Le client envoie le nom du fichier.
  2. Le serveur génère une "Signed URL" Cloudflare R2 valide 1h (GetObject/PutObject).
  3. Le serveur retourne l'URL.
  4. L'app upload le fichier directement vers Cloudflare R2 en PUT.
  
  POST /upload/confirm
  5. L'app confirme l'upload. Le serveur sauvegarde l'ID et l'ID utilisateur dans Supabase DB.

  GET /download/:id
  1. Le destinataire visite le lien.
  2. Le serveur vérifie Supabase DB.
  3. Le serveur génère une "Signed URL" de téléchargement R2 et redirige l'utilisateur (Redirect 302).
  4. Le fichier est marqué `downloaded = true`.

  CONVERSION (Flux End-to-End)
  ─────────────────────────────────────────────────────────
  POST /convert/[type]
  1. L'app envoie le fichier au serveur.
  2. Le serveur convertit via LibreOffice/ImageMagick/Poppler.
  3. Le serveur retourne le fichier converti.
  4. L'app propose de télécharger ou de transférer le fichier directement.

============================================================
  7. HISTORIQUE DES DÉCISIONS & RÉSOLUTION DE BUGS
============================================================

  A. Déploiement Initial du Serveur Express
  ─────────────────────────────────────────────────────────
  - Objectif : Recevoir fichier HTTP → Supabase Storage → Retourner ID → Download via ID.
  - Étapes : Structure dossiers → Init Node.js → Config .env → Supabase services → Endpoints → Tests.

  B. Problème de compatibilité Node.js en Production
  ─────────────────────────────────────────────────────────
  - Symptôme : Crash du serveur lors du déploiement initial.
  - Cause : La plateforme utilisait Node 18 par défaut. `@supabase/supabase-js` récent requiert Node 20 (APIs WebSocket natives).
  - Solution : Ajout de `"engines": { "node": ">=20.0.0" }` dans `package.json` pour forcer la version.

  C. Problème "Lien expiré ou invalide" après Upload
  ─────────────────────────────────────────────────────────
  - Symptôme : Même après un upload réussi, le téléchargement échouait immédiatement.
  - Cause racine : Le code supprimait la ligne de la base de données PENDANT l'envoi du fichier, et non APRÈS. Les navigateurs faisant souvent deux requêtes HTTP (ex: pré-chargement), la deuxième trouvait la ligne déjà supprimée par la première.
  - Solution : Utilisation de l'événement `res.on('finish')`. La suppression s'effectue désormais de manière différée (après 60 secondes) garantissant que la réponse HTTP est 100% transmise au client avant le nettoyage.

  D. Écran blanc (Crash) lors de la génération du QR code
  ─────────────────────────────────────────────────────────
  - Symptôme : Lors de l'envoi d'un ou plusieurs fichiers, la barre de progression atteint 100% puis l'écran devient complètement vide, sans QR code ni lien.
  - Cause racine : Deux erreurs combinées. L'adresse du backend dans le code mobile comportait une faute de frappe (`https://-faas-transfer...`). Lors du crash silencieux de la requête, le frontend tentait de générer un QR code avec un lien vide, ce qui faisait crasher le composant `react-native-qrcode-svg`.
  - Solution : Correction de l'URL du backend vers `https://faas-transfer.onrender.com` dans `send.tsx` et `receive.tsx`.

  E. Problème de Transfert Multiple (ZIP) et Saturation Mémoire
  ─────────────────────────────────────────────────────────
  - Symptôme : Le transfert de plusieurs fichiers échouait côté serveur, ou générait une archive corrompue difficile à ouvrir sur mobile.
  - Cause racine : 
    1. Le serveur chargeait l'intégralité du ZIP dans la RAM avant l'envoi à Supabase, ce qui plantait les petits serveurs (Render).
    2. Les noms de fichiers avec espaces cassaient la commande de compression.
    3. Le nom final de l'archive n'était pas défini (`undefined`), corrompant parfois l'extension.
  - Solution : Passage sur une lecture en continu (Stream) via `fs.createReadStream()`. Protection des chemins de fichiers avec des guillemets dans la commande `zip` et forçage de l'option `-j` pour éviter l'inclusion de dossiers temporaires. Génération d'un nom de fichier sécurisé "Archive de X fichiers.zip".

  8. RÉFÉRENCEMENT NATUREL (SEO) SUR GOOGLE
============================================================

  Le référencement (SEO) permet à l'application d'apparaître 
  dans les résultats de recherche Google quand on tape "FaaS Transfer".
  Étant donné que c'est une application dynamique (React/Expo), 
  Google a besoin d'aide pour la lire.

  A. FICHIERS STATIQUES (Dossier : mobile/public/)
  ─────────────────────────────────────────────────────────
  - robots.txt : Fichier lu en premier par les robots de Google. 
    Il leur donne la permission d'explorer toutes les pages du site.
  - sitemap.xml : C'est le "plan de la ville". Il liste toutes 
    les pages importantes (Accueil, Envoyer, Recevoir, Convertir) 
    pour que Google n'en rate aucune.

  B. BALISES META (Fichier : mobile/src/app/_layout.tsx)
  ─────────────────────────────────────────────────────────
  - Composant <Head> d'expo-router : Injecte des balises HTML invisibles.
  - <title> : Le grand titre bleu cliquable sur Google.
  - <meta name="description"> : Le petit texte descriptif noir en dessous du titre.
  - <meta property="og:..."> : (Open Graph) Les images et textes qui 
    s'affichent quand on partage le lien sur WhatsApp, Twitter ou LinkedIn.

  C. PROCÉDURE DE MISE EN LIGNE (GOOGLE SEARCH CONSOLE)
  ─────────────────────────────────────────────────────────
  Une fois les balises meta et le sitemap créés, voici les étapes pour 
  forcer Google à référencer l'application (à faire soi-même sur le web) :
  
  1. Se connecter à Google Search Console : https://search.google.com/search-console
  2. Ajouter une propriété via "Préfixe de l'URL" (ex: https://faas-transfer.vercel.app).
  3. Valider la propriété avec la méthode "Balise HTML" :
     - Copier la balise `<meta name="google-site-verification" content="..." />`
     - La coller dans le `<Head>` du fichier `_layout.tsx`.
     - Faire un `git commit` et un `git push`.
     - Attendre le déploiement sur Vercel (environ 2 minutes).
     - Cliquer sur le bouton "VALIDER" sur Google Search Console.
  4. Une fois validé en vert, aller dans le menu "Sitemaps" (à gauche).
  5. Entrer `sitemap.xml` et cliquer sur "Envoyer".
  
  Résultat : Google scanne officiellement le site et l'affiche dans ses 
  recherches dans les jours qui suivent.

  9. LIMITES TECHNIQUES DE L'ARCHITECTURE ET CRASHS MÉMOIRE
============================================================

  A. Diagnostic des Crashs (Vidéos et envois multiples)
  ─────────────────────────────────────────────────────────
  Symptôme : Lors de l'envoi de gros fichiers (vidéos de 100Mo+) ou de plusieurs dizaines de photos, l'application simulait le chargement jusqu'à 90% puis crashait ou retournait à l'accueil silencieusement.
  
  Cause racine sur le Téléphone (Frontend) :
  Le code utilisait `await fetch(file.uri).blob()` pour convertir le fichier avant de l'envoyer. Cette méthode charge l'intégralité du fichier dans la mémoire vive (RAM) du téléphone. Pour une vidéo de 200 Mo, l'application tente d'allouer 200 Mo de RAM instantanément. Le navigateur mobile ou l'OS tue alors le processus pour éviter la saturation.
  
  Cause racine sur le Serveur (Backend) :
  Le serveur lisait également le fichier entier en RAM via `fs.readFileSync()` avant de l'envoyer à Supabase. Le serveur Render (Plan Gratuit) ne possédant que 512 Mo de RAM, il crashait lors de l'envoi de fichiers trop lourds.

  Solutions techniques implémentées (Détail fichier par fichier) :
  
  [MODIFY] mobile/src/app/send.tsx
  - Importation de `Platform` depuis `react-native`.
  - Remplacement du chargement destructif en RAM (`await fetch(file.uri).blob()`) par un envoi direct du fichier depuis le disque local du téléphone en utilisant `formData.append('file', { uri: file.uri, name: file.name, type: file.mimeType })`.
  - Application de cette logique optimisée pour l'envoi d'un fichier unique ET pour les envois multiples. Le téléphone "stream" le fichier au serveur au lieu de le mettre en mémoire vive.

  [MODIFY] server/routes/upload.js
  - Dans la route `/` (envoi simple), remplacement de la lecture totale en mémoire (`fs.readFileSync`) par un stream asynchrone (`fs.createReadStream`) couplé à l'option `duplex: 'half'`.
  - Résultat : Cela crée un tuyau de données direct entre le serveur Render et le stockage Supabase, sans jamais stocker le gros fichier dans la petite RAM (512 Mo) du serveur.

  B. Limites de la "Stack" Actuelle (Version Gratuite)
  ─────────────────────────────────────────────────────────
  Voici les limites techniques imposées par nos hébergeurs gratuits actuels :

  1. Render (Backend Node.js) :
     - RAM : 512 Mo maximum. (Totalement contourné grâce à l'utilisation des Streams évoquée ci-dessus).
     - Veille : Le serveur s'endort après 15 minutes d'inactivité. Le premier transfert peut donc prendre 30 secondes de plus à démarrer le temps que le serveur se réveille.

  2. Supabase (Base de données et Stockage) :
     - Base de données : 500 Mo gratuits (suffisant pour des millions d'entrées).
     - Stockage Total : 1 Go d'espace disque maximum.
     - Limite de taille de fichier par défaut : 50 Mo par fichier. Si vous essayez d'envoyer un fichier de 60 Mo, Supabase le bloquera. 
       *Solution : Vous pouvez modifier cette limite dans les paramètres de votre projet Supabase (Dashboard > Storage > Policies/Settings).*

  3. Vercel (Frontend Web) :
     - Bande passante : Limite de base de 100 Go/mois.
     - Taille des requêtes : Comme nos fichiers transitent entre le téléphone et notre serveur Render (et non pas vers Vercel), Vercel n'impose aucune limite sur le poids de nos transferts !


============================================================
  10. HISTORIQUE DES BUGS RÉSOLUS (ET SOLUTIONS)
============================================================
Ce journal permet de garder une trace de toutes les anomalies rencontrées durant les tests, et de la manière précise dont elles ont été réglées.

  Bug 1 : Le serveur injoignable et l'écran bloqué
  ─────────────────────────────────────────────────────────
  Symptôme : Le chargement montait jusqu'à 100%, puis l'application devenait silencieuse ou affichait une page vide, sans jamais générer de QR code ni de lien.
  Problème : Dans le code de l'application (`mobile/src/app/send.tsx` et `receive.tsx`), l'adresse du serveur backend était mal orthographiée avec un tiret en trop : `https://-faas-transfer.onrender.com`. Cette adresse n'existait pas, la connexion échouait silencieusement.
  Solution : J'ai supprimé le tiret erroné dans les deux fichiers pour restaurer la bonne URL : `https://faas-transfer.onrender.com`.

  Bug 2 : Les QR Codes généraient un lien mort (Railway)
  ─────────────────────────────────────────────────────────
  Symptôme : Après un transfert réussi, le QR Code scanné par un autre téléphone renvoyait vers une page d'erreur Railway.
  Problème : Le backend (`server/routes/upload.js`) générait manuellement le lien de téléchargement (downloadUrl) qu'il renvoyait au téléphone. Ce lien était encore "codé en dur" avec l'ancien nom de domaine de notre premier hébergeur (Railway).
  Solution : J'ai modifié `upload.js` dans la fonction d'upload simple et d'upload multiple, pour remplacer l'ancienne adresse par la nouvelle URL Render correcte.

  Bug 3 : Mauvais logo dans la recherche Google (Logo Vercel)
  ─────────────────────────────────────────────────────────
  Symptôme : En faisant une recherche sur Google ou en envoyant le lien par WhatsApp, c'était le logo par défaut de Vercel (le petit triangle noir) qui apparaissait.
  Problème : Le site web ne possédait pas de "favicon" officiel configuré avec notre logo.
  Solution : J'ai repris le code SVG du logo que j'avais dessiné pour la barre de menu (le "F" bleu/violet avec la flèche). Je l'ai converti en un véritable fichier image (`favicon.svg`, `favicon.png` et `favicon.ico`) que j'ai placé dans le dossier `mobile/public/` et `mobile/assets/images/`. C'est désormais notre identité visuelle officielle.

  Bug 4 : Erreurs de syntaxe JSX (Fichiers en rouge dans l'éditeur)
  ─────────────────────────────────────────────────────────
  Symptôme : Les fichiers `index.tsx`, `send.tsx` et `convert.tsx` s'affichaient en rouge dans votre éditeur (erreurs de code bloquantes).
  Problème : Des balises React (comme `<ActionCard />`) n'étaient pas correctement fermées. De plus, il y a eu une tentative d'utiliser des commentaires classiques `/* */` directement dans le rendu HTML/JSX, ce qui fait planter React Native.
  Solution : J'ai harmonisé la syntaxe des fichiers, refermé toutes les balises correctement et utilisé la syntaxe de commentaire valide pour JSX : `{/* commentaire */}`.

  Bug 5 : L'effet de brillance (Glow) absent sur les blocs principaux
  ─────────────────────────────────────────────────────────
  Symptôme : Vous m'aviez signalé que le grand bloc de l'interface "ne brillait pas" et manquait de dynamisme.
  Problème : Les propriétés d'ombres (boxShadow, shadowColor, elevation) n'étaient pas correctement calibrées pour se superposer au fond sombre, rendant le bloc plat.
  Solution : J'ai ajusté les valeurs de `shadowOpacity`, `shadowRadius` et ajouté des bordures lumineuses subtiles pour donner ce côté professionnel et "néon" à l'application.

  Bug 6 : L'impossibilité de sélectionner/envoyer plusieurs fichiers (100 photos)
  ─────────────────────────────────────────────────────────
  Symptôme : L'application ne permettait pas de sélectionner plusieurs fichiers d'un coup, ce qui gâchait l'utilité pour les gros envois (saisons de séries, albums photos).
  Problème : Le sélecteur de fichier (`DocumentPicker`) n'avait pas l'option multiple activée, et le backend ne savait gérer qu'un seul fichier à la fois.
  Solution : J'ai activé `multiple: true` dans le DocumentPicker, et j'ai créé une toute nouvelle route backend (`/multiple`) capable de recevoir plusieurs fichiers et de les archiver en un seul fichier ZIP robuste avant de l'envoyer sur Supabase.

============================================================
Le test de 8 secondes (23 Mo) qui prend 40 secondes et reste bloqué à 90% a mis en lumière deux problèmes majeurs dans l'architecture initiale. Pour envoyer des vidéos de 1 heure (plusieurs Gigaoctets) en quelques minutes, l'architecture a été modifiée.

Les deux problèmes initiaux :
1. La fausse barre de progression (Bloquée à 90%) : Dans le code initial de `send.tsx`, l'application utilisait une fausse animation qui montait automatiquement à 90% en quelques secondes (`setInterval`). Elle attendait ensuite que le serveur ait fini son travail pour passer à 100%.
2. Le goulot d'étranglement du serveur (Double Upload) : Le fichier faisait le trajet `Téléphone -> Serveur Render -> Supabase`. Le fichier voyageait deux fois sur le réseau, et le serveur Render agissait comme un goulot.

La Solution Ultime implémentée : "Direct Upload" (L'autoroute)
L'architecture a été modifiée pour créer une autoroute directe entre le téléphone et Supabase. Le serveur Render sert uniquement de "Guichet".
1. Le téléphone demande au serveur Render : "Je veux envoyer un fichier".
2. Le serveur Render génère un ticket d'accès sécurisé (Signed URL) via Supabase et le renvoie en 0.1s.
3. Le téléphone utilise ce ticket pour uploader le fichier directement à Supabase (1 seul voyage).

Modifications techniques appliquées :
- `server/routes/upload.js` : Création d'une route pour générer des Signed URLs Supabase (retrait de `multer` pour les gros fichiers).
- `mobile/src/app/send.tsx` : Utilisation de `FileSystem.createUploadTask` d'Expo au lieu de `fetch()` pour un suivi de progression 100% réel.
- Librairie `react-native-zip-archive` : Ajoutée pour zipper les fichiers multiples directement en local sur le téléphone avant de les envoyer sur "l'autoroute" Direct Upload.

# Architecture "Hyper-Parallèle" (S3 Multipart)

Pour répondre à ton ambition de surpasser les limites physiques d'une seule connexion et permettre l'envoi de fichiers immenses (ex: 50 Go, 8 saisons d'une série), nous devons changer fondamentalement notre façon d'envoyer les données.

Actuellement, on utilise un "Tuyau Unique" (Single PUT). Si la connexion vacille, le tuyau ralentit. 

Je te propose de coder l'**Architecture S3 Multipart Hyper-Parallèle**. C'est la technologie utilisée par YouTube et Google Drive pour l'envoi de très gros fichiers.

## 🚀 Le Concept (Comment tricher avec la physique)

Au lieu d'envoyer la vidéo de 50 Go d'un coup dans 1 seul tuyau, l'application va :
1. **Découper** virtuellement la vidéo en 10 000 morceaux de 5 Mo directement sur le téléphone (sans exploser la RAM).
2. **Ouvrir 4 à 6 tuyaux en même temps** vers Cloudflare.
3. Envoyer les morceaux en parallèle. 
4. Cloudflare va "recoller" les morceaux à l'arrivée.

**Pourquoi c'est révolutionnaire pour la vitesse ?**
Sur les antennes 4G/5G, les opérateurs brident souvent la vitesse par "connexion" (ex: 2 Mo/s max par tuyau). En ouvrant 4 tuyaux en parallèle, on force l'antenne à nous donner 4 fois plus de bande passante (jusqu'à 8 Mo/s). C'est le secret des "Download Accelerators".

RAPORT DE TRAVAIL :

C'est une excellente question, et c'est tout à fait normal de se sentir perdu ici. Il y a un paradoxe apparent : on t'a toujours dit "si tu charges un gros fichier en mémoire, la RAM explose", et là, tu envoies 1,39 Go d'un coup sans découper, et ça marche !

Voici le secret : tu ne charges pas le fichier en mémoire. Ton code utilise ce qu'on appelle un flux continu (un Stream), et non un chargement en bloc.

Voici concrètement comment l'architecture V1 optimisée (le flux unique) réussit cet exploit par rapport aux anciennes méthodes.

**Le problème original : L'approche "Bloc" (qui fait exploser la RAM)**
Avant, le problème ne venait pas du fait d'envoyer le fichier en une seule fois, mais de la façon dont JavaScript le lisait. Souvent, les développeurs utilisaient des méthodes comme `FileReader.readAsArrayBuffer()` ou tentaient de stocker le fichier dans une variable pour l'envoyer.

Le processus était :
1. Lire l'intégralité du fichier de 1,39 Go depuis le disque.
2. Copier ce 1,39 Go dans la RAM du navigateur.
3. Tenter de l'envoyer sur le réseau.

Résultat : Le navigateur d'un smartphone n'a pas 1,39 Go de RAM libre allouée à un seul onglet. L'OS tue l'application ("Uffa!").

**Le Chunking (Découpage) : Une solution de contournement**
La première solution qu'on t'avait proposée (le découpage avec `File.slice()`), c'était de tricher avec cette mémoire :
- Couper le fichier virtuellement.
- Ne charger en RAM que 5 Mo à la fois.
- Envoyer ces 5 Mo, les effacer de la RAM, et passer aux 5 Mo suivants.

Ça marche très bien sur ordinateur. Mais sur Android, le système de sécurité (qui contrôle l'accès à tes photos) panique quand un script web essaie de "découper" un fichier de sa galerie en temps réel. Ça génère des erreurs XHR.

**La solution actuelle : Le "Streaming" natif (Le tuyau ouvert)**
L'architecture que tu as finalement utilisée exploite une capacité moderne des navigateurs (souvent via l'API fetch avec le corps de la requête sous forme de Stream ou simplement en passant directement l'objet File natif à une requête XHR/Fetch). Dans ce scénario, JavaScript ne "lit" pas le fichier.

1. **Création du pointeur :** Le fichier reste sur le disque. Lorsque l'utilisateur sélectionne la vidéo, JavaScript ne reçoit qu'une référence (un pointeur) vers le fichier sur le disque du téléphone. Aucune donnée vidéo n'est copiée en RAM.
2. **Ouverture du tuyau réseau :** Passage du relais au navigateur. JavaScript dit au moteur du navigateur (en C++) : "Ouvre une connexion HTTP directe vers Cloudflare (via l'URL pré-signée) et envoie ce fichier-là."
3. **Le streaming bit à bit :** Le transfert invisible. Le navigateur agit comme un entonnoir direct entre le disque dur du téléphone et la carte réseau. Il aspire les données du disque par minuscules blocs (de l'ordre du kilo-octet), les met dans le réseau, et les oublie. La RAM n'est utilisée que comme une zone de transit temporaire et minuscule.

**Pourquoi c'est une victoire sur l'OS**
C'est une victoire parce que tu as arrêté d'utiliser JavaScript pour faire le travail lourd. Au lieu de dire à JavaScript : "Découpe ce fichier et gère les envois" (ce qui déclenche les sécurités Android), tu as simplement dit au moteur profond du navigateur : "Tiens, voilà le fichier, connecte-le à Cloudflare, et débrouille-toi".

L'OS mobile adore ça. Il n'y a pas de violation de sécurité (JavaScript n'a pas farfouillé dans la vidéo), et la gestion de la mémoire est parfaite (le C++ du navigateur est infiniment plus optimisé que JavaScript pour faire transiter des octets du disque vers la carte réseau).

3. Amélioration des flex-scaling (flex: 1 vs flex: 1.5) pour éviter l'écrasement des textes sur petits écrans.
4. Centralisation des styles premium (ombres, bordures) pour un rendu professionnel.

=== MISE À JOUR : SYSTÈME DE DRAG & DROP HYBRIDE ET NUMÉROTATION DES PLACES ===
Afin de rendre l'interface de conversion parfaitement fluide sur le Web et répondre au besoin précis de réorganisation des fichiers (ex: ordre de fusion PDF), une refonte technique du Drag & Drop a été implémentée dans `mobile/src/app/convert.tsx` :

1. Architecture et Contournement de React Native Web (HTML5) :
   - Constat Technique : Le composant natif `<View>` de React Native Web (qui se traduit en `div`) filtre certains événements DOM natifs et bloque l'initialisation du Drag & Drop HTML5 classique (le navigateur annule immédiatement l'action).
   - Solution Brute : Mise en place d'un rendu conditionnel agressif basé sur `Platform.OS === 'web'`. Sur le Web, on force le rendu d'une vraie balise HTML native `<div>` avec l'attribut strict `draggable={true}`.
   - Gestion stricte du `dataTransfer` : Pour que Chromium et WebKit autorisent le glissement, l'événement `onDragStart` extrait l'objet via `e.nativeEvent.dataTransfer` (SyntheticEvent React) et lui injecte obligatoirement une donnée via `.setData('text/plain', index)`. De même, l'événement `onDragOver` utilise `.dropEffect = 'move'` avec un `.preventDefault()` obligatoire.

2. Interchangeabilité des Places (Swap Logic Algorithmique) :
   - L'algorithme de Drop ne se contente plus d'insérer (`Array.splice`) le fichier au milieu (ce qui causait des décalages imprévisibles).
   - Implémentation d'un "Swap" direct (permutation) :
     `const draggedFile = newFiles[draggedIndex];`
     `const targetFile = newFiles[index];`
     `newFiles[index] = draggedFile;`
     `newFiles[draggedIndex] = targetFile;`
   - Résultat : Les places physiques sont strictement interchangeables. Lâcher l'élément A sur l'emplacement B permute instantanément leurs deux places.

3. Logique de Numérotation Statique (Slots) :
   - UX : Pour la fusion PDF, ce ne sont pas les fichiers qui possèdent un numéro de séquence, mais bien leurs "Places" (Slots) d'accueil sur l'interface.
   - Un composant Badge (`position: absolute`, `top: 8`, `left: 8`) a été ajouté dynamiquement sur la grille.
   - La valeur est calculée sur le moment via l'index de la grille `(index + 1)`, indépendamment du fichier contenu. Peu importe le fichier glissé, la première case physique de gauche restera toujours la place "1".
   - Ajout d'un état dynamique `dragOverIndex` qui déclenche un feedback visuel natif (bordure verte et opacité modifiée) lors du survol d'une place cible.

4. UI/UX et Affordance (Prévention des casses) :
   - Problème des noms de fichiers extrêmes : Certains fichiers (ex: `li_assicurazione_RSM_Assistenza_cittadini_stranieri_Extra_U.E...`) ne possédaient aucun espace, brisant le layout et rendant le composant gigantesque.
   - Solution : Application stricte de `<Text numberOfLines={1} ellipsizeMode="middle" width="100%">`. Cela force la troncature (`...`) au centre du nom de fichier, préservant ainsi l'extension visible à droite (ex: `.pdf`) sans casser la grille.
   - Guidage Utilisateur (Affordance) : Ajout d'un encart visuel dynamique sous le titre ("Maintenez et glissez un fichier pour modifier l'ordre") couplé à une icône de permutation (`swap-horizontal-outline`). Ce composant ne s'affiche intelligemment que lorsque la liste contient plus d'un élément (`selectedFiles.length > 1`).

### Outil Diviser PDF (Split-PDF) : Traitement 100% Client-Side
1. Objectif de performance absolue :
   - Pour éviter de télécharger un PDF potentiellement lourd de 50 pages sur le backend juste pour compter ses pages, nous utilisons une architecture "Zéro Serveur" en exécutant le fractionnement localement sur le Web et Mobile.
2. Dépendances de manipulation :
   - `pdf-lib` et `jszip` : Chargés de manière **dynamique** (`await import(...)`) au moment de l'action utilisateur (`initSplitPDF` et `handleSplitPDF`).
   - *Note sur le crash Vercel (SSG) et l'Import Dynamique :* Lors de l'itération précédente, un import statique global avait été utilisé pour pallier un problème de compilation. Cependant, l'import statique de librairies lourdes manipulant des ArrayBuffers (comme `pdf-lib`) provoque un crash total (page blanche) lors du rendu statique côté serveur (SSG / Static Rendering) par Expo Router sur Vercel. Le retour définitif à l'import dynamique à l'intérieur des fonctions asynchrones résout le problème : la page `/convert` s'affiche instantanément, et la librairie n'est téléchargée par le navigateur que lorsque l'utilisateur clique sur "Diviser PDF", optimisant le poids du bundle et évitant le crash SSG.
   - Ils permettent d'ouvrir le buffer du fichier original, lire le nombre de pages (`getPageCount()`) et copier les pages voulues vers de nouveaux documents virtuels.
   - `jszip` : Déjà existant dans le projet. Permet d'encapsuler la volée des mini-PDF (générés sous forme d'Uint8Array) dans une archive sans appel API.
3. Représentation Graphique de la Coupe :
   - Un état `split_editor` remplace le `staging` pour la division PDF.
   - Une grille rend itérativement les pages de `0` à `pageCount - 1`. 
   - Entre chaque page (index `i`), un composant de coupe (icône "Ciseaux") s'affiche. Si l'utilisateur clique dessus, l'index `i` est poussé dans le tableau de statut `splitPoints`. Le style est alors mis à jour (couleur `danger` : rouge, au lieu de `border-dashed`).
4. Téléchargement Universel :
   - L'archive finale (`zip.generateAsync({ type: 'blob' })`) est servie différemment. Sur Web, nous utilisons `URL.createObjectURL(blob)` injecté dans une balise `<a>`. Sur Mobile, c'est l'API native `expo-file-system` qui écrit le base64 dans `cacheDirectory`, puis invoque `expo-sharing` pour l'enregistrement.

### 12 Août 2026 - Crash Silencieux "Diviser PDF" et Vercel SSG
- **Contexte :** Implémentation de la fonction "Diviser PDF" en local avec `pdf-lib` et `jszip`.
- **Problème n°1 (Fausse Piste de l'Import Dynamique) :** L'application ne réagissait pas au clic sur le bouton d'ouverture. La cause initiale était que l'import dynamique `await import('pdf-lib')` échouait en silence car le module `pdf-lib` manquait dans le `package.json` sur Vercel (oubli du commit `package.json`). L'erreur silencieuse renvoyait l'utilisateur à l'état initial sans message clair.
- **Problème n°2 (Crash SSG avec Imports Statiques) :** En pensant résoudre l'erreur d'import dynamique, un import statique `import { PDFDocument } from 'pdf-lib'` a été placé en haut de `convert.tsx`. Conséquence : une fois le `package.json` poussé, le déploiement Vercel a réussi, **mais la page `/convert` est devenue totalement blanche sur le navigateur client**. Raison technique : les imports statiques de modules Node.js lourds ou non conçus pour être évalués au top-level dans le contexte du Static Rendering (SSG) d'Expo Web crashent le rendu global de la page.
- **Problème n°3 (ChunkLoadError avec Imports Dynamiques) :** Le retour à l'import asynchrone `await import('pdf-lib')` a continué de causer des échecs (absence de réaction) car le bundler Metro/Webpack de Vercel peinait à générer et résoudre correctement les chunks asynchrones (ChunkLoadError) de cette lourde librairie dans le navigateur.
- **Solution Définitive :** Remplacement de `await import(...)` par des `require('...')` synchrones mais *inline* (à l'intérieur du gestionnaire de clic `initSplitPDF` et `handleSplitPDF`). 
  *Avantages de cette approche :*
  1. Le `require` force Metro à inclure la dépendance dans le bundle principal (fini les 404 ChunkLoadErrors).
  2. Puisqu'il est invoqué à l'intérieur d'une fonction, il n'est **pas évalué** lors du SSG de Vercel. Le crash de la page blanche est évité.
  3. L'exécution est robuste et instantanée au clic.
- **Bonus UI :** Intégration d'un `window.alert` explicite pour le Web afin de s'assurer qu'aucune erreur ne sera jamais silencieuse à l'avenir.

### 12 Août 2026 à 23h52 et 10 secondes - Correction de l'erreur "__extends of undefined" (tslib)
- **Contexte :** Après le déploiement sur Vercel de la rustine utilisant `require('pdf-lib')` en ligne, l'application ne crashe plus au chargement (SSG sain). Cependant, au clic sur "Ouvrir", l'alerte `window.alert` que nous avions ajoutée a révélé l'erreur exacte : `Cannot destructure property '__extends' of 'n.default' as it is undefined`.
- **Analyse du Problème :** Cette erreur est un bug classique du bundler Metro d'Expo Web. Lorsque Metro tente d'importer le paquet `pdf-lib`, il doit également transpiler et résoudre ses sous-dépendances, notamment `tslib` (les helpers TypeScript). Sur le Web, Metro résout mal le `default export` de `tslib`, ce qui provoque le crash de la destructuration `__extends` à l'exécution de la librairie, rendant `pdf-lib` inutilisable malgré un build réussi.
- **Action Réalisée :** Modification du code dans `convert.tsx` pour ne plus requérir le point d'entrée classique de la librairie. À la place, nous avons forcé Metro à ignorer la résolution des sous-dépendances en ciblant directement le bundle UMD pré-compilé et minifié fourni par les auteurs de la librairie : `require('pdf-lib/dist/pdf-lib.min.js')`. 
- **Résultat :** Le bundle UMD contient déjà la librairie entière avec tous ses helpers TypeScript injectés en interne, évitant totalement à Metro Web d'avoir à interpréter `tslib`. L'outil de découpe s'initialise désormais parfaitement sur le navigateur Web, avec des performances maximales.
